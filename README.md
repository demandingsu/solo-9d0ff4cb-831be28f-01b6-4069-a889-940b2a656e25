# 冷库 A/B 除霜策略耗电对比分析

Flask + SQLite 的小型分析网页：导入「轮次计划」「实际切换记录」「每分钟用电量」三份 CSV，
按轮次给出有效配对数和 **B − A 平均耗电差**，并逐分钟列出哪些配对因何剔除；
在网页上更正切换时刻后，只重算受影响轮次。另有**峰段转移试算**入口：选一轮并填写
覆盖整个 A 窗的计费时段，评估用有效分钟对的 B 电量替换 A 电量后，计费时段峰值需量
（最高连续 15 分钟平均功率）的变化上下界。

## 快速开始（Docker Compose）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

数据落在命名卷 `coldstore-data` 的 `/data/coldstore.sqlite3`；容器重启数据仍在。

本地开发运行（需要 Python 3.11+ 与 Flask）：

```bash
python -m pip install -r requirements.txt
COLDSTORE_DB=./data/coldstore.sqlite3 python -m coldstore.web
# 或 flask --app coldstore.web run
```

## CSV 格式

所有时间均为 **UTC 整分钟**，接受 `YYYY-MM-DD HH:MM`、`YYYY-MM-DDTHH:MM`、末尾 `Z` 或 `+00:00`；
拒绝非整分钟、非 UTC 偏移。表头大小写与首尾空格不敏感。

**轮次计划** `rounds.csv`

| 列 | 含义 |
| --- | --- |
| `round_id` | 轮次编号，唯一 |
| `a_start`, `a_end` | A 窗 `[a_start, a_end)` |
| `b_start`, `b_end` | B 窗 `[b_start, b_end)` |

校验：两窗等长、互不重叠（首尾相接允许）、终点晚于起点。

**实际切换记录** `switches.csv`

| 列 | 含义 |
| --- | --- |
| `switched_at` | 从这一分钟起实际策略变为 `strategy` |
| `strategy` | `A` 或 `B` |
| `round_id` | 可选；留空 = 对全部轮次生效，填写 = 仅作用于该轮 |

**每分钟用电量** `readings.csv`

| 列 | 含义 |
| --- | --- |
| `minute` | UTC 整分钟 |
| `kwh` | 该分钟耗电量（kWh，非负） |

`examples/` 下有三份可直接导入的示例，覆盖：

| 轮次 | 预期 | 场景 |
| --- | --- | --- |
| R1 | 60 有效对 | 正常 |
| R2 | 45 有效对 | A 窗起点才切回 A（前 10 分钟不足）；B 窗第 5 分钟才切 B |
| R3 | 44 有效对 | B 窗第 5 分钟才切 B；另有 2 个分钟缺读数 |
| R4 | 30 有效对 | 两次切换都恰好提前 10 分钟，边界有效 |
| R5 | 不可比较 | B 窗内实际仍是 A → 全部 20 对剔除 |

## 计算口径

1. **配对**：A 窗第 *i* 分钟与 B 窗第 *i* 分钟配对（相同分钟偏移）。
2. **有效对**：同一偏移上
   * A、B 两侧都有用电读数；且
   * 该分钟的实际策略分别等于计划策略 A / B；且
   * 该分钟距该策略区间起点 ≥ 10 分钟（即已按该策略连续运行满 10 分钟）。

   任一侧不满足，整对剔除，并记录具体原因（缺读数 / 策略不符 / 无法确认策略 / 未满 10 分钟）。
3. **汇总**：有效对数的 `(B − A)` 算术平均，单位 kWh/分钟；正值表示 B 更耗电。
   没有有效对 → 该轮 `不可比较`，平均值为空。
4. **连续运行**从切换记录给出的策略区间起点算起；同策略的重复记录会合并，不打断连续性。
   时间窗左闭右开，终点那一分钟不属于窗口。

### 更正与增量重算

- 更正切换时刻（以及可选策略、作用轮次）后，比较**更正前后每个计划窗内逐分钟的
  `(实际策略是否正确, 是否已运行满 10 分钟)` 状态**；状态有任何变化才重算该轮。
- 因此切换记录落在窗外也可能触发重算（例如把 B 窗前的切换从 12:50 改到 12:51，
  B 窗 13:00 起就不再满 10 分钟）；窗内切换若没有改变任何分钟状态则不会重算。
- 切换记录更新、该轮配对明细、汇总在同一事务内提交；任何异常整体回滚，
  原记录与旧结果保持可查。每次导入/更正都写入 `audit_log`。

## 峰段转移试算

入口：总览页「前往峰段转移试算」按钮，或直接打开 `/trial`；程序化调用可用
`POST /api/trials`（JSON 字段 `round_id` / `billing_start` / `billing_end` /
`missing_cap_kwh`）。**试算全程只读**：不写回 `readings` / `switches` /
`results`，也不写 `audit_log`。

### 输入约束

- 选一轮；计费时段 `[billing_start, billing_end)` 为 UTC 整分钟、含起点不含终点，
  时长 15 分钟至 24 小时，且必须**完整覆盖该轮 A 窗**（可向两侧外延）。
- 填写缺测分钟的**每分钟电量上限**（非负 kWh）。

### 计算口径

1. 配对与读数取当前**已提交状态**（即 `result_pairs` 缓存 + `readings` 表）；
   切换更正并重算后再试算，自动使用更新后的配对。计费时段内没有任何有效对时
   返回 400 并提示，不出结果。
2. 计费时段内，每个**有效分钟对**对应的 A 分钟电量替换为 B 分钟电量
   （增量 Δ = B − A），其余分钟照旧；被替换的分钟两侧都有读数，不可能是缺测。
3. 计费时段内没有读数的分钟为**缺测分钟**，其电量 `x ∈ [0, 上限]`，
   **替换前后共用同一个值**。
4. 替换前、替换后分别取时段内最高的连续 15 分钟平均功率（kW = 窗内 kWh 合计 × 4），
   两种情形的峰段可以不同。
5. 输出需量差 `D = 替换后峰值 − 替换前峰值` 随缺测取值能达到的**上下界**：
   - 上界 ≤ 0 → **确定降峰**（缺测取任何允许值都不会抬高需量）；
   - 下界 ≥ 0 → 确定抬升；其余为无法确定（或持平）。
6. 上界 > 0 时，给出一组确实会抬高需量的缺测取值（落在某个 15 分钟窗内的缺测分钟
   取上限、其余取 0）以及替换前后的峰段，供值班员按分钟补查；同时给出「缺测全 0」
   「缺测全上限」两个参照情形的峰值与峰段。

### 上下界算法（无额外依赖）

设 n 为计费分钟数、`W = n − 14` 个 15 分钟窗，`S_j`、`S'_j = S_j + Δ_j` 分别为
第 j 窗替换前后电量合计，`D(x) = 4·(max_j S'_j(x) − max_k S_k(x))`。展开 max 后
每项是关于缺测变量的仿射函数，系数只可能是 −1/0/+1 且符号由「缺测分钟是否在窗 w 内」
决定，因此全局最大/最小都在角点赋值 `x^(w)`（窗 w 内缺测取上限、其余取 0）上取得：

```
max D = 4·max_w ( S'_w(x^(w)) − max_k S_k(x^(w)) )
min D = 4·min_w ( max_k S'_k(x^(w)) − S_w(x^(w)) )
```

配合前缀和每个窗求和 O(1)，整体 O(W²)；24 小时最坏情形（W=1426）实测约 3.4 秒。
测试中用小规模穷举（角点 + 内部点）交叉验证了上下界与 witness 赋值。

## 数据库结构

`rounds`（轮次计划）、`switches`（切换记录，可更正）、`readings`（分钟读数）、
`results`（每轮汇总缓存）、`result_pairs`（逐对明细与剔除原因）、`audit_log`（操作日志）。

## 已知限制 / 待办

- 10 分钟连续运行按**每个配对分钟**判断（因此窗内切换会只剔除窗首若干对）。
  若业务要求「整窗都必须提前 10 分钟已运行」，只需改为按窗首判定。
- 切换记录只表达「从某分钟起策略变为 X」，不表达切换耗时/过渡分钟；如需过渡期
  不可用，可作为额外剔除原因加入。
- 导入为**全量替换**（三份文件一起换），不支持追加或单轮增量导入。
- 未做鉴权与多用户隔离；生产部署需替换 `COLDSTORE_SECRET` 并置于反向代理之后。
- 本环境无 Docker，`Dockerfile` / `docker-compose.yml` 按标准写法提供但**未实际构建运行**；
  已用本地 Python 进程 + 示例 CSV 完成端到端 HTTP 自测（导入、展示、跨窗更正、
  峰段转移试算的峰段转移/缺测/更正联动三类场景；服务以与容器相同的 gunicorn 命令启动）。
- 峰段转移试算的上下界假设缺测分钟电量在 `[0, 上限]` 内**各自独立**变化；若业务上
  缺测分钟之间存在联动约束（如总电量限额），当前模型不表达，需要再扩展。
- 试算每次实时计算、不落库也不记日志，无法回看历史试算参数与结果；如需留存可另加
  只读之外的 `trials` 表（当前按“试算不写回原数据”的要求刻意不做）。
- 24 小时最坏规模（1426 个 15 分钟窗）单次试算约 3 秒量级，同步请求可接受但没有
  做异步任务/超时保护；更大窗口受 24 小时上限约束不会再增长。
- 更正失败（输入非法、记录冲突）与重算异常都会回滚；但若进程在提交后崩溃，
  以 SQLite 事务保证的前一状态为准，没有额外的 WAL 备份/恢复界面。
- 页面一次渲染全部轮次与全部配对明细（示例规模很快）；轮次或分钟数很大时
  需要分页或按需加载 `/api/rounds/<id>/pairs`。
